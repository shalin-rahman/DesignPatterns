1 · THE CORE IDEA
From Code Smells to Prompt Smells
What is a code smell?
A surface sign in source code that something may be wrong 
beneath , not a bug, but a warning.
Familiar example: Long Method
A method doing too much is hard to read, test, and reuse. 
Developers recognize it on sight.
How developers respond
They refactor: split responsibilities, clarify names, isolate 
behavior , without changing what the code does.
The same idea, applied to prompts
A prompt can also carry warning signs. Ronanki et al. (2024) 
call these prompt smells.
C O D E
Bad code  →  Long Method  →  refactored code
One giant method handling validation, calculation, and
output is split into small, named, single-purpose methods.
P R O M P T
Bad prompt  →  Prompt Bloat  →  refactored 
prompt
An over-decorated persona and buried request are
reduced to a direct, well-scoped instruction.
A prompt smell is a surface-level indicator in a prompt's wording or structure that correlates with a higher risk of an undesirable 
AI response.

1

A prompt with no obvious smell can

3

Smells raise the probability of a bad 
outcome , shifting the odds is why 
prompt quality needs evaluation, 
not just intuition.

Ambiguous References
C O N T E X T
A software project meeting is being summarized for 
the next steps.
W H Y I T ' S A P R O B L E M
Who is “they”?
What is “it” referring to?
Which problem , of possibly several?
Rule of thumb: if a pronoun could refer to more than 
one noun in the prompt, replace it with the noun.
SMELLY PROMPT
“The team changed it because they found a problem. Explain 
what they should do next.”
↓
REFACTORED 
PROMPT
Name the project, the team, the specific artifact that changed, 
and the specific problem found , before asking what should 
happen next.

Overloaded Prompt
C O N T E X T
A student is developing a library management 
system.
W H Y I T ' S A P R O B L E M
Analogous to a method doing too many things
Each phase needs different context to do well

“Design the requirements, UML diagrams, database,

↓
REFACTORED 
PROMPT

prompt, and one reviewed output, per stage.

Unnecessary Repetition
C O N T E X T
A student asks the AI to explain inheritance.
W H Y I T ' S A P R O B L E M
Same instruction repeated in different words
No new information is added by repeating
Directly analogous to duplicate code
Connect to code smells: this is duplicate code, 
restated as instructions instead of statements.
SMELLY PROMPT
“Explain inheritance in simple language. Keep it simple. Make 
it easy. Don’t make it complicated. Use simple words and a 
simple example.”
↓
REFACTORED 
PROMPT
“Explain inheritance using simple language and one Java 
example for beginners.”

PART II  ·  SMELL 4 OF 4
Conflicting Constraints
C O N T E X T
Writing an executive report for stakeholders.
W H Y I T ' S A P R O B L E M
“Comprehensive” and “exactly 100 words” pull in 
opposite directions
The model must silently choose which constraint to 
break
Tension is invisible until the output disappoints
Refactoring resolves the tension by naming exactly 
what “comprehensive” must include within the limit.
SMELLY PROMPT
“Write a comprehensive report covering all aspects of the 
project in exactly 100 words.”
↓
REFACTORED 
PROMPT
“Write a 100-word executive summary covering the project’s 
objective, three key findings, major risk, and recommendation.”

Just like refactoring never changes what a program is supposed to do, prompt refactoring never 
changes what you're asking for , only how clearly, completely, and unambiguously you ask for it.

A Practical Refactoring Pattern
INTENT
What outcome do 
you actually want?
→
CONTEXT
Who / what / where 
does this apply to?
→
TASK
The specific action 
to perform
→
CONSTRAINTS
Limits: length, tone, 
scope, exclusions
→
OUTPUT
Exact shape: table, 
list, code, format
→
EVALUATION
How will you judge 
the result?
Then transform one bad prompt step-by-step, adding exactly one missing stage at a time so students can see which 
change fixed what.
E X A M P L E A P P L I C A T I O N
“Give me a Java payment example using a design pattern.”  →  applying INTENT (clear pattern comparison) + 
CONTEXT (varying payment methods) + TASK (implement Strategy) + OUTPUT (class structure + runnable example) 
yields a fully specified prompt , see the worked example next.

PART IV · PROMPT REFACTORING
Full Example: From Bad Prompt to Good Prompt
SCENARIO: A university course-registration system
v1 , Smelly
“Design a good modern secure course registration system for our university.”
v2 , Add context
+ Institution type, student population, existing systems it must integrate with.
v3 , Clarify task
+ Specific deliverable: e.g. “propose the system architecture and core entities.”
v4 , Add constraints
+ Security requirements, scale, technology constraints, timeline.
v5 , Define output
+ “Provide a component diagram, a data model, and a short risk list.”
Students watch the prompt being refactored incrementally , exactly like code , and see which single addition changes the output 
most.

WHY THIS MATTERS FOR SOFTWARE ENGINEERING STUDENTS
Requirements engineering already trains students to interrogate ambiguity, missing stakeholders, and conflicting 
constraints. Running that same discipline on a prompt , instead of a requirements document , makes prompt quality 
feel like a natural extension of a skill they already have, not a new one.

APPLIED PRACTICE
Case Study: Programming / Design Pattern
“Write code for a payment system using a suitable design pattern.”
Students identify the ambiguity first: which pattern? which payment methods? what does “suitable” mean here?
REFACTORED
“Design a Java payment-processing example where the payment method can vary between 
CreditCard, bKash, and PayPal. Use the Strategy pattern. Provide the class structure and a small 
runnable example.”
Now students can see how design-pattern thinking , naming the varying behavior, choosing Strategy, specifying 
participants , improves prompts the same way it improves code.

Research Limitations
!
Prompt-smell research is still emerging
!
The 2026 taxonomy is preliminary, not final
!
Smells are context-dependent , the same phrasing can smell in one setting and not another
!
A smell does not guarantee a bad output
!
Removing a smell does not guarantee a good output
Treat the catalogue in this deck as a teaching tool for building intuition , not as a certified, exhaustive checklist.

Designing Prompts Is a Design Discipline
✓
Prompt smells are warning signs, not verdicts.
✓
Context matters , the same prompt can be fine or flawed depending on it.
✓
Clear prompts reduce ambiguity for both humans and models.
✓
Complex prompts can often be decomposed, just like complex methods.
✓
Output requirements should be made explicit, not assumed.
✓
Prompt refactoring is directly analogous to code refactoring.
✓
Good prompts are designed, inspected, and refined , not merely written.
