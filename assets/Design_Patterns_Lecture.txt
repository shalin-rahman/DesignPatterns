What is a design pattern?
A typical, reusable solution to a 
commonly occurring problem in 
software design.
Think of it as a blueprint: the layout and features are 
fixed, but you decide how to build it in your own code.
A pattern is…
•
a named, described solution
•
a language-independent template
•
proven across many projects
A pattern is not…
•
ready-to-paste code or a library
•
an algorithm (a fixed recipe of steps)
•
a rule you must always follow
Recurring problem
Seen again and again in 
different projects

Singleton
Exactly one instance, with one global access point
I N T E N T
Guarantee a class has only one instance and

A N A L O G Y

public class Logger {
  private static Logger instance;
 
  private Logger() { }             // no outside "new"
 
  public static synchronized Logger getInstance() {
    if (instance == null) instance = new Logger();
    return instance;
  }
}

STRUCTURAL PATTERN
Decorator
Add responsibilities by wrapping objects
Whip  +$0.40
Mocha  +$0.70
Milk  +$0.50
Espresso  $2.00
cost() = 2.00 + 0.50 + 0.70 + 0.40 = $3.60
I N T E N T
Attach new behavior to an object dynamically by wrapping it 
in objects that share its interface.
W H Y
Subclassing every combination (milk + mocha + whip…) 
explodes into dozens of classes. Wrapping composes 
behavior at runtime.
J A V A
Coffee c = new Espresso();      // $2.00
c = new Milk(c);                // + $0.50
c = new Mocha(c);               // + $0.70
c = new Whip(c);                // + $0.40
System.out.println(c.cost());   // 3.60
Seen in: new BufferedReader(new FileReader(path))

BEHAVIORAL PATTERN
Observer
Notify many objects when one object changes
Channel (Subject)
+ subscribe(s)
+ unsubscribe(s)
+ upload(video)
«Subscriber»
PhoneApp
+ update(video)
«Subscriber»
EmailDigest
+ update(video)
«Subscriber»
Dashboard
+ update(video)
update()
new video uploaded
Analogy: a newspaper subscription. Subscribe and every issue 
arrives; cancel and it stops, the publisher never needs to know 
who is reading.
I N T E N T
Define a one-to-many dependency so that dependents 
are notified automatically when the subject changes.
J A V A
interface Subscriber { void update(String v); }
 
class Channel {
  List<Subscriber> subs = new ArrayList<>();
 
  void subscribe(Subscriber s) { subs.add(s); }
  void upload(String v) {
    subs.forEach(s -> s.update(v));
  }
}
Seen in: DOM addEventListener, Redux/React 
subscriptions, pub/sub messaging

CRITICAL VIEW
Use patterns wisely
16 / 23
GoF patterns that Peter Norvig 
showed are simplified or eliminated 
by language features in Lisp or 
Dylan.
Rule of thumb  
Start simple (KISS, YAGNI). Refactor 
toward a pattern when real pain appears: 
duplicated code, ripple-effect changes.
Over-engineering
When you own a hammer, 
everything looks like a nail. Do 
not add patterns “just in case”.
Language 
workarounds
Some patterns compensate for 
missing language features, 
such as first-class functions.
Copy-paste adoption
Applying a pattern unchanged, 
without adapting it, can add 
duplication and inefficiency.
Fuzzy foundations
Critics call patterns ad hoc and 
not always distinct from 
ordinary abstraction, MVC 
predates them.
