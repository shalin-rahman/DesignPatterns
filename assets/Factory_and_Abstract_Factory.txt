Factory

Any method that creates objects,

Factory Method & Abstract Factory
6
FACTORY METHOD
When to use it
1
The exact types are not known beforehand
Separate construction from use. To add a new product, add a new creator subclass and override the factory 
method, nothing else changes.
2
Users should be able to extend your framework
Reduce the code that constructs components to one factory method. Someone overrides it (e.g., 
createButton() returns a RoundButton) and the framework uses their component.
3
You want to reuse existing objects
A constructor must return a new object. A factory method can look in a pool or cache first, useful for large 
objects like database connections.

REFACTORING
The refactoring recipe
Refactoring.Guru’s steps, applied to the notification service
1
Make all products follow one interface
interface Notification { void send(...); }
2
Add an (empty) factory method to the creator
Notification createNotification() { return null; }
3
Replace product constructor calls with the 
factory method
Notification n = createNotification();
4
Create a creator subclass per product; override 
the method
class SmsService extends NotificationService { ... }
5
Make the base factory method abstract
protected abstract Notification createNotification();

public abstract class NotificationService {
 
    // the factory method: subclasses decide the product
    protected abstract Notification createNotification();
 
    public void notifyUser(String to, String message) {
        Notification n = createNotification();
        String text = message.trim();  // business logic
        System.out.println("[log] "
                + getClass().getSimpleName());
        n.send(to, text);
    }
}

FACTORY METHOD
Advantages and limitations
Advantages
No tight coupling between creator and concrete 
products
Single Responsibility: creation code in one place
Open/Closed: new products without breaking clients
Business logic in the creator is reused for every 
product
Limitations
Many new subclasses, best added to an existing 
creator hierarchy
Can be overkill for small, simple applications
A static creation method cannot be overridden, it 
defeats the pattern
All products need a common interface
Related patterns: Factory Method specializes Template Method; many designs start here and evolve towards Abstract 
Factory, Prototype or Builder.

interface Command {
    void execute(Connection c, String sql);
    default void requireDialect(Connection c, String want) {
        if (!c.dialect().equals(want))
            throw new IllegalStateException(
                getClass().getSimpleName()
                + " cannot run on '" + c.dialect() + "'");
    }
}
 
class MySqlCommand implements Command {
    public void execute(Connection c, String sql) {
        requireDialect(c, "mysql");
        System.out.println("[mysql] executing: " + sql);
    }
}
 
class PostgresCommand implements Command {
    public void execute(Connection c, String sql) {
        requireDialect(c, "postgres");
        System.out.println("[postgres] executing: " + sql);
    }
}

class AuditService {
    private final DatabaseFactory factory;
 
    AuditService(DatabaseFactory factory) {
        this.factory = factory;

        Connection conn = factory.createConnection();
        // products from ONE factory always match

public class AbstractFactoryDemo {
 
    // the ONLY place that knows the concrete factories
    static DatabaseFactory factoryFor(String db) {
        switch (db) {
            case "mysql":    return new MySqlFactory();
            case "postgres": return new PostgresFactory();
            default:
                throw new IllegalArgumentException(
                        "Unknown db: " + db);
        }
    }
 
    public static void main(String[] args) {
        String[] dbs = { "mysql", "postgres" };
 
        for (String db : dbs) {
            System.out.println("--- " + db + " ---");
            new AuditService(factoryFor(db)).log();
        }
    }
}

ABSTRACT FACTORY
Advantages and limitations
Advantages
Products from one factory are guaranteed 
compatible
No tight coupling between concrete products and 
clients
Single Responsibility: creation code in one place
Open/Closed: new variants without breaking clients
Limitations
Many new interfaces and classes
Overkill for small projects
A new product type changes the abstract factory 
and every concrete factory
Something must choose the concrete factory at 
start-up
Related patterns: often built from Factory Methods (or Prototypes); factories are routinely Singletons; Builder returns its product 
after several steps, Abstract Factory returns it immediately.

Key
takeaways
1
Both patterns keep client code away from concrete 
classes.
2
Factory Method: one product, chosen by a subclass 
(inheritance).
3
Abstract Factory: a family of matching products, chosen 
by a factory object (composition).
4
A simple factory or static creation method is a useful first 
step, but not either pattern.
5
Adding variants is easy in both; adding a new product 
type is hard for Abstract Factory.
