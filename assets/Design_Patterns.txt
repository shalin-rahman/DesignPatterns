FOUNDATIONS
What Is Software Design?
The process of deciding what components should exist, 
what responsibilities each has, how objects communicate, 
and how the system will absorb future change.
Ask these questions early:
•
What happens when PayPal / bKash is added?
•
What if SMS notifications are required?
•
What if the database engine changes?
// naive design: everything in one class
class Order {
  calculateTotal()
  processPayment()
  sendEmail()
  generateInvoice()
  saveToDatabase()
  printReceipt()
}
It works at first: but every new requirement forces a change inside 
this one class.

DESIGN PRINCIPLES
SOLID Principles
S
Single Responsibility
A class should have one responsibility, one reason to change.
O
Open/Closed
Open for extension, closed for modification: avoid growing if/else chains.
L
Liskov Substitution
A subtype must be usable wherever its base type is expected.
I
Interface Segregation
Don't force clients to depend on methods they don't use.
D
Dependency Inversion
Depend on abstractions, not concrete implementations.
11
DESIGN PRINCIPLES
DRY, KISS & YAGNI
DRY
Don't Repeat Yourself
Avoid duplicating logic: but don't 
over-abstract to remove every 
similarity.
KISS
Keep It Simple
Avoid unneeded complexity. 
Simplicity should be appropriate, not 
minimal at all costs.
YAGNI
You Aren't Gonna Need It
Don't build for hypothetical future 
requirements: build for the real one.

IMPROVING EXISTING CODE
Refactoring: Structure Changes, Behavior Doesn't
Refactoring changes a program's internal structure without changing what it does externally.
void generateInvoice() {
  // calculate tax
  // calculate discount
  // format invoice
  // save invoice
  // send email
}
void generateInvoice() {
  calculateTax();
  calculateDiscount();
  formatInvoice();
  saveInvoice();
  sendEmail();
}
Refactoring
Small structural changes to existing code: same behavior, 
better design. Usually incremental.
Rewriting
Building a new implementation, potentially with a different 
architecture altogether.

MINI CASE STUDY
A Poorly Designed Ordering System
class Order {
  void process(String paymentType) {
    if (paymentType.equals("CARD")) {
      // card payment
    } else if (paymentType.equals(
        "BKASH")) {
      // bKash payment
    }
    // save order, generate invoice,
    // send email, send SMS
  }
}
Discuss in pairs:
•
How many responsibilities does Order have?
•
Which SOLID principles are violated?
•
What problems appear as the system grows?
•
Which classes could be extracted?
•
Could a pattern eventually help: should we jump there now?
Suggested extraction:
Order   •   PaymentService   •   InvoiceGenerator   •   OrderRepository   •

A MINDSET SHIFT
Problem-First, Not Pattern-First
✕  Pattern First
•
“I learned Factory.”
•
“Where can I use Factory?”
Leads to over-engineering and misapplied patterns.
✓  Problem First
•
“I have an object-creation problem.”
•
“What's causing it?”
•
“Which principles apply?”
•
“Would Factory Method help?”
This approach produces better software design.

WEIGHING THE TRADE-OFF
Benefits vs. Limitations of Patterns
Benefits
•
Reusability of proven design ideas
•
A common vocabulary between developers
•
Improved maintainability
•
Greater flexibility to new requirements
•
Clearer communication about architecture
Limitations
•
Overengineering: 5 classes where 1 would do
•
Added abstraction and complexity
•
Misapplication to the wrong problem
•
A learning curve for maintainers
•
A false sense of quality
